What is BankFlow? (Simple Explanation)

Think of BankFlow as a simplified version of HDFC or SBI's digital banking backend. When a customer opens the app, they can check their balance, transfer money to someone, apply for a loan, and get notified when any transaction happens. All of this is handled by 7 separate backend services that work together.

✅
Why 7 services? Think of a real bank — there's a separate department for accounts, one for loans, one for fraud, one for customer service. Each team is independent. If the loan department has an issue, the accounts department still works. That's microservices.
ServiceBank AnalogyWhat It Does
API GatewayBank's main doorRoutes customers to right department, checks ID (JWT)
User ServiceCustomer RelationsRegister, login, KYC verification
Account ServiceAccounts DepartmentOpen accounts, check balance, debit/credit
Transaction ServiceCashier / TellerProcess deposits, withdrawals, transfers
Loan ServiceLoans DepartmentApply, approve, calculate EMIs
Notification ServiceSMS/Email teamSend alerts for every transaction
Fraud DetectionRisk DepartmentFlag suspicious transactions

Step 2: User Service — JWT, BCrypt, Spring Security

🎯
This is the most important section. 70% of interview questions will be about JWT and Spring Security.

User.java — implements UserDetails

@Entity
@Table(name = "users")
public class User implements UserDetails {
    // @Id, @Column fields...

    @Enumerated(EnumType.STRING)
    private Role role;  // CUSTOMER or ADMIN

    // Spring Security requires these methods:
    @Override
    public Collection<?> getAuthorities() {
        return List.of(new SimpleGrantedAuthority("ROLE_" + role.name()));
        // ROLE_CUSTOMER or ROLE_ADMIN
    }

    @Override public boolean isEnabled() { return status == UserStatus.ACTIVE; }
    // If status is SUSPENDED → isAccountNonLocked() returns false → login blocked
}
✅
Why implements UserDetails? Spring Security needs to understand your User class. By implementing UserDetails, you're telling Spring: "Here's how to check if this user is enabled, what their authorities are, what their password is." Spring Security then uses this for authentication automatically.

JWT Flow

// 1. Login request arrives
// 2. AuthenticationManager validates: BCrypt.check(inputPassword, storedHash)
// 3. If valid, JwtService creates token:
Jwts.builder()
    .subject(user.getEmail())          // who is this for?
    .claim("role", user.getRole())     // embed role in token
    .issuedAt(new Date())              // when created?
    .expiration(after24hours)           // when it expires?
    .signWith(secretKey)                // sign with HMAC-SHA256
    .compact();                         // build to "header.payload.signature"

// 4. Client stores token in localStorage
// 5. Every request: Authorization: Bearer eyJhbGc...
// 6. JwtAuthenticationFilter (OncePerRequestFilter) validates on every call
💡
BCrypt explained: BCrypt is a one-way hash. "password123" → "$2a$10$Xa3bcd...". It's one-way — you can NEVER reverse it. Each hash has a unique "salt" built in. When logging in, BCrypt hashes the input and compares. This prevents rainbow table attacks.

SecurityConfig — The Rules

// Spring Security 6 — Functional DSL (no WebSecurityConfigurerAdapter)
http
    .csrf(disable)               // REST APIs don't need CSRF
    .cors(configure)             // Allow React (localhost:3000)
    .authorizeRequests()
        .requestMatchers("/api/auth/**").permitAll()     // no token for login/register
        .requestMatchers("/api/users/**").hasRole("ADMIN") // only ADMIN
        .anyRequest().authenticated()                   // everything else needs JWT
    .sessionManagement(STATELESS)   // no sessions — JWT handles state
    .addFilterBefore(jwtFilter, ...);  // our filter runs first

Step 3: Account Service — JPA, Balance, Debit/Credit

Account Types

  • SAVINGS — Standard savings account with interest
  • CURRENT — Business account, no interest but higher transaction limits
  • FIXED_DEPOSIT — Fixed term, higher interest rate
  • RECURRING_DEPOSIT — Monthly deposits for a fixed period

debit() and credit() with @Transactional

@Transactional  // If anything throws → database change is ROLLED BACK
public void debit(String accountNumber, BigDecimal amount) {
    Account account = accountRepository.findByAccountNumber(accountNumber)
        .orElseThrow(() -> new AccountNotFoundException(...));

    if (account.getStatus() == AccountStatus.FROZEN)
        throw new AccountFrozenException("Account is frozen");

    if (account.getBalance().compareTo(amount) < 0)
        throw new InsufficientFundsException("Balance: " + account.getBalance());

    account.setBalance(account.getBalance().subtract(amount));
    accountRepository.save(account);
    // If save fails, entire transaction rolls back
}
✅
We use BigDecimal (not double or float) for money! Double arithmetic has floating-point errors — 10.00 - 9.99 might be 0.009999999 in double. BigDecimal is exact for decimal arithmetic.

Step 4: Transaction Service

Transfer Flow

// Customer calls: POST /api/transactions/transfer
public ApiResponse transfer(String userId, TransferRequest req) {
    // 1. Validate: fromAccount != toAccount
    if (req.getFromAccount().equals(req.getToAccount()))
        throw new TransactionException("Cannot transfer to same account");

    // 2. Create transaction record
    String txnId = "TXN-" + UUID.randomUUID().toString().substring(0, 12).toUpperCase();
    Transaction txn = Transaction.builder()...build();
    transactionRepository.save(txn);

    // 3. Publish to Kafka (async — returns immediately)
    kafkaTemplate.send("transfer.initiated", Map.of(
        "transactionId", txnId,
        "fromAccount", req.getFromAccount(),
        "amount", req.getAmount().toString()...
    ));

    // 4. Also trigger fraud check asynchronously
    kafkaTemplate.send("fraud.check.request", Map.of(...));

    // 5. Return success immediately (don't wait for fraud check)
    return ApiResponse.success(mapToResponse(txn), "Transfer initiated");
}

Step 5: Loan Service — EMI Formula

EMI Calculation

// EMI = P × r × (1+r)^n / ((1+r)^n - 1)
// P = Principal, r = monthly rate = annual/1200, n = months

private BigDecimal calculateEmi(BigDecimal principal, BigDecimal annualRate, int months) {
    double r = annualRate.divide(BigDecimal.valueOf(1200), 10, HALF_UP).doubleValue();
    double n = months, p = principal.doubleValue();
    double emi = p * r * Math.pow(1 + r, n) / (Math.pow(1 + r, n) - 1);
    return BigDecimal.valueOf(emi).setScale(2, HALF_UP);
}

// Example: ₹5,00,000 Personal Loan, 12% p.a., 36 months
// r = 12/1200 = 0.01
// EMI = 500000 × 0.01 × (1.01)^36 / ((1.01)^36 - 1) = ₹16,607.15

Step 6: Fraud Detection — Rule-Based Scoring

public void analyzeTransaction(Map txnData) {
    BigDecimal amount = new BigDecimal(txnData.get("amount").toString());
    int riskScore = 0;

    // Rule 1: Large transaction
    if (amount.compareTo(BigDecimal.valueOf(500000)) > 0) riskScore += 40;

    // Rule 2: High-risk amount
    if (amount.compareTo(BigDecimal.valueOf(100000)) > 0) riskScore += 20;

    // Rule 3: Debit transactions are higher risk
    if ("WITHDRAWAL".equals(type) || "TRANSFER".equals(type)) riskScore += 10;

    // Rule 4: Round numbers suggest structuring
    if (amount.remainder(BigDecimal.valueOf(10000)).equals(BigDecimal.ZERO)) riskScore += 5;

    if (riskScore >= 30) {
        // Create FraudAlert record + publish to "fraud.alert" Kafka topic
        createAlertAndNotify(txnData, riskScore);
    }
}

✅
The Notification Service is stateless — it doesn't have a database. It just consumes Kafka events and triggers notifications. If it goes down, Kafka holds the messages (based on consumer group offset) and delivers them when it comes back up.

Step 14: Interview Q&A (12 Questions)

Q: Explain your BankFlow project in 2 minutes
A: "I built a full enterprise banking system using microservices architecture. It has 7 Spring Boot services: API Gateway routes requests and validates JWTs; User Service handles registration and authentication with JWT and BCrypt; Account Service manages savings and current accounts; Transaction Service processes deposits, withdrawals, and IMPS/NEFT/RTGS transfers; Loan Service handles loan applications with EMI calculation; Notification Service sends alerts via Kafka; and Fraud Detection scores every transaction using rule-based logic. The whole system is containerized with Docker Compose, uses Redis for caching and JWT blacklisting, Apache Kafka for async event communication, and has a React 18 frontend."
Q: Why 7 microservices? Why not one app?
A: "Each service has a single responsibility. If the Loan Service crashes, customers can still check their balance and make transactions. Each service can be scaled independently — if transfer volume is high, I can run 5 Transaction Service instances without touching other services. Each service has its own PostgreSQL database (database-per-service pattern), so changes to one schema don't affect others. Teams can work independently, deploy independently, and use different technologies if needed."
Q: How does JWT authentication work in your project?
A: "JWT is stateless authentication. When a user logs in, the User Service creates a JSON Web Token signed with our secret key using HS256 algorithm. The token contains the user's email and role in the payload. It's returned to the React client which stores it in localStorage. Every subsequent API call includes it in the Authorization header. Each backend service has a JwtAuthenticationFilter (extends OncePerRequestFilter) that extracts the token, verifies the signature using the same secret key, checks expiry, and sets the authenticated user in Spring's SecurityContext. If signature is invalid or token is expired, it returns 401 Unauthorized."
Q: What is Redis and how did you use it?
A: "Redis is an in-memory key-value data store. I use it in three ways: First, JWT blacklisting — when a user logs out, I add the token to Redis with TTL equal to its remaining expiry. The JWT filter checks Redis before accepting any token, so logged-out tokens are immediately rejected even though they're technically still valid JWT tokens. Second, account balance caching — I cache balances for 60 seconds to reduce PostgreSQL queries on the accounts_db. Third, OTP storage with 5-minute TTL — Redis automatically expires the key, no cleanup job needed."
Q: How does fund transfer work between services?
A: "The Transaction Service receives the transfer request and creates a transaction record. It then publishes two Kafka events asynchronously: one to 'transfer.initiated' (picked up by Notification Service to send SMS/email) and one to 'fraud.check.request' (picked up by Fraud Detection to analyze the transaction). The Transaction Service returns success immediately without waiting — this is non-blocking and gives customers instant confirmation. In a production system, I'd also call the Account Service to debit/credit balances, but that's via REST or Kafka."
Q: How does fraud detection work?
A: "Every transaction triggers a Kafka message to 'fraud.check.request'. The Fraud Detection Service applies 4 rules: amounts over ₹5 lakh add 40 risk points, amounts over ₹1 lakh add 20, debit transactions add 10, round numbers (potential structuring) add 5. If the total score reaches 30 or above, a FraudAlert record is created in the fraud_db and a 'fraud.alert' Kafka event is published — which triggers the Notification Service to send alerts to both the customer and the security team."
Q: Explain the EMI calculation
A: "EMI uses the reducing balance formula: EMI = P × r × (1+r)^n / ((1+r)^n − 1), where P is the principal, r is the monthly interest rate (annual rate / 1200), and n is the tenure in months. For example, a ₹5 lakh Personal Loan at 12% for 36 months gives ₹16,607/month. When a loan is approved, I generate the full amortization schedule — a table showing each monthly EMI split into principal and interest components. Early EMIs have more interest; later ones have more principal. The schedule is stored in the emi_schedule table."
Q: What is a circuit breaker in the API Gateway?
A: "A circuit breaker prevents cascade failures. If the Account Service is down, without a circuit breaker, every request to /api/accounts would hang for the connection timeout (maybe 30 seconds) before failing. The circuit breaker monitors failures and after a threshold, 'opens' — immediately returning a fallback response (HTTP 503) instead of trying to connect to the failed service. This protects the gateway from thread exhaustion and gives customers an immediate, meaningful error instead of hanging. I configured it in Spring Cloud Gateway with fallback URIs for each service."
Q: How would you scale BankFlow for high traffic?
A: "Each service is stateless (JWT, no server sessions), so I can run multiple instances behind a load balancer. For example, 5 Transaction Service instances. Kafka partitions allow parallel processing — 10 partitions means 10 consumers can process simultaneously. PostgreSQL gets read replicas for heavy read workloads. Redis cluster for high availability. The API Gateway would be fronted with an Nginx load balancer. For even higher scale, I'd add Kubernetes for orchestration, horizontal pod autoscaling based on CPU/memory metrics."
Q: What happens if Kafka goes down?
A: "Kafka has built-in fault tolerance with message persistence. Messages are stored on disk even after delivery. If the Notification Service is down, Kafka holds the messages (commits offset only after processing). When the service restarts, it re-reads from the last committed offset. For producer side, if Kafka is unavailable, I'd implement a retry mechanism with exponential backoff and store failed events in an outbox table as a fallback pattern. For the transaction flow, the core transaction still succeeds — only notifications might be delayed."
Q: How is BCrypt different from SHA-256?
A: "Both are hash functions, but BCrypt is designed specifically for passwords. SHA-256 is fast — an attacker can compute billions per second trying to brute force. BCrypt is intentionally slow — it has a configurable 'work factor' (cost parameter). BCrypt also automatically generates a unique random salt for each password, so two users with the same password have different hashes (preventing rainbow table attacks). With $10 work factor, BCrypt takes ~100ms to hash — fast enough for login but too slow for brute force attacks."
Q: What is the difference between @Transactional at service vs repository level?
A: "@Transactional at the service method level wraps the entire method in one database transaction. If anything throws inside the method, all database changes are rolled back. At repository level, Spring Data auto-applies @Transactional to individual CRUD methods. I use service-level @Transactional for operations that touch multiple database entities — like debit+credit in a transfer. If the credit fails after the debit, @Transactional ensures the debit is also rolled back, preventing money from disappearing."
